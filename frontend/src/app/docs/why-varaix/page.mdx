# Why Varaix

VaraiX is not trying to be a drop-in replacement for every plotting stack. It is aimed at a narrower problem: generating compact, deterministic SVG charts from a small, line-oriented language that is easy to read, diff, and automate.

If your current options are Python Matplotlib or JavaScript Chart.js, VaraiX is a better fit when you care about one or more of these goals:

- short specs that are easy to hand-edit
- deterministic output that stays stable across runs
- SVG that works in browsers, docs, slides, and static sites
- simple text files that LLMs and scripts can generate reliably
- fewer moving parts than a runtime-heavy charting stack

## Comparison at a glance

| Goal | VaraiX | Matplotlib | Chart.js |
| --- | --- | --- | --- |
| Spec size | Very small, line-oriented | Usually more verbose Python code | Often more setup and configuration |
| Output | Deterministic SVG | Mostly image-oriented, can export SVG | Browser-first canvas/SVG workflows |
| Automation | Strong fit for generated text | Good, but Python runtime is required | Good, but JavaScript runtime is required |
| Git diffs | Easy to review | Can be noisy once plots get complex | Config objects can get large |
| Browser portability | Native SVG output | Needs export or embedding | Runs in the browser |
| Advanced analytics | Limited by design | Very strong | Strong for interactive dashboards |

## Where VaraiX wins

### 1. Faster to author and review

A `.vix` file is intentionally small. That makes it easier to:

- generate from templates
- review in code review
- tweak by hand without touching a full program

### 2. Better for deterministic publishing

VaraiX renders to SVG with a stable input/output relationship. That is useful when the same chart needs to appear in documentation, static exports, and CI-generated artifacts without visual drift.

### 3. Better for LLM and script generation

Because the language is compact and line-oriented, it is easier for tooling to produce valid chart specs than to synthesize a full Python or JavaScript plotting program.

### 4. Easier to embed in content workflows

The output is a plain SVG, so it fits naturally into docs, slides, and websites without an extra chart runtime.

## Where Matplotlib or Chart.js are still better

Use Matplotlib when you need deep statistical plotting, scientific workflows, or rich Python ecosystem integration.

Use Chart.js when you need highly interactive dashboards, client-side updates, or an established JavaScript charting stack.

VaraiX is meant to be smaller and more opinionated than both.

## How to prove it in practice

If you want to make the case inside this repository, the strongest evidence is not marketing copy. It is a repeatable comparison:

1. Build the same chart in VaraiX, Matplotlib, and Chart.js.
2. Compare lines of code and amount of setup.
3. Re-run the chart generation and show that the VaraiX SVG stays identical.
4. Show that the VaraiX source is easier to diff and easier to generate automatically.

## Benchmark snapshot

Below is one concrete benchmark using the same monthly revenue line chart in all three tools. Token counts were measured on the source text with a GPT tokenizer so the comparison is consistent and reproducible.

| Metric | VaraiX | Matplotlib | Chart.js |
| --- | --- | --- | --- |
| Source tokens | 50 | 87 | 141 |
| Characters | 136 | 303 | 463 |
| Lines | 8 | 13 | 24 |

### Benchmark inputs

VaraiX:

```vix
chart: line
title: Monthly Revenue
x: month
y: revenue ($k)

myData = [["Jan", 12], ["Feb", 19], ["Mar", 15], ["Apr", 22]]

data: myData
```

Matplotlib:

```python
import matplotlib.pyplot as plt

months = ["Jan", "Feb", "Mar", "Apr"]
values = [12, 19, 15, 22]

plt.figure(figsize=(6, 4))
plt.plot(months, values, marker="o")
plt.title("Monthly Revenue")
plt.xlabel("Month")
plt.ylabel("Revenue ($k)")
plt.tight_layout()
plt.savefig("monthly_revenue.svg")
plt.close()
```

Chart.js:

```javascript
import Chart from "chart.js/auto";

const ctx = document.getElementById("chart");
const labels = ["Jan", "Feb", "Mar", "Apr"];
const values = [12, 19, 15, 22];

new Chart(ctx, {
	type: "line",
	data: {
		labels,
		datasets: [{
			label: "Revenue ($k)",
			data: values,
			borderColor: "#4a90d9",
			tension: 0.25
		}]
	},
	options: {
		responsive: true,
		plugins: {
			title: { display: true, text: "Monthly Revenue" }
		}
	}
});
```

### What the numbers show

- VaraiX uses the fewest source tokens, because the chart description is compact and declarative.
- Matplotlib stays reasonably small, but still needs Python setup and explicit figure management.
- Chart.js is the heaviest of the three here because the browser-oriented configuration is more verbose.

If you want a stronger presentation, repeat this same measurement across several chart types and add averages.

## Extra validation ideas

If you want more evidence beyond source size, these are the three best follow-up tests:

1. LLM window test: generate the same chart 50 times with each tool and compare token usage, syntax failures, and broken outputs.
2. Null data test: compare how much defensive cleaning code is required for missing values versus using `null_fill` in VaraiX.
3. Security validation: compare the attack surface of parsed chart text versus chart code that executes inside a runtime.

## Benchmark

If you want this page to support a production-grade claim, treat benchmarking as a repeatable measurement suite, not a one-off demo. Run every test on the same machine, with the same dataset, the same chart types, and the same output target. Record the median of at least 10 runs, plus p95 where latency matters.

### Benchmark rules

- Use the same chart specification goals across tools: one line chart, one bar chart, one scatter plot, and one pie chart.
- Measure both cold and warm runs when the tool has a startup cost.
- Capture the exact source text, exact rendered artifact size, and exact error output for failed runs.
- Report median, p95, and failure rate instead of a single best-case result.
- Store the raw benchmark inputs and outputs in version control so results can be reproduced.

### Production-grade benchmarks to run

| Benchmark | What it measures | Metric(s) | Why it matters |
| --- | --- | --- | --- |
| Chart authoring size | How much source is needed to express the same chart | Tokens, characters, lines | Shows how compact the language is |
| LLM generation reliability | How often an LLM produces valid chart specs | Success rate, syntax error rate, retry count | Measures how friendly the syntax is to automation |
| Parse throughput | How fast a chart file is parsed | ms per file, files/sec | Matters for CI and batch generation |
| Render throughput | How fast SVG is produced | ms per render, renders/sec | Core runtime cost |
| Cold start cost | How long first use takes | time-to-first-render | Important for CLI and browser startup |
| Warm run cost | How fast repeated renders are | median latency | Useful for bulk generation |
| Memory usage | How much RAM is needed during parse/render | peak RSS, heap delta | Matters for CI and server-side workloads |
| Output determinism | Whether repeated runs match exactly | byte-for-byte diff, hash match | Critical for reproducible builds |
| SVG size | How large the final artifact is | bytes, gzip bytes | Affects docs and delivery cost |
| Null handling cost | How much extra code is needed for missing data | extra lines, extra tokens, failure count | Highlights `null_fill` value |
| Error quality | How useful failures are | parse error clarity, line accuracy | Helps debugging and automation |
| Security robustness | How the system behaves with malicious input | blocked payloads, crash rate, sandbox safety | Shows the advantage of a parsed language |
| Cross-chart consistency | Whether chart types follow the same grammar | template reuse rate | Demonstrates design consistency |
| CI suitability | Whether the benchmark is stable in automation | flake rate, pass rate | Important for production workflows |

### Suggested real benchmark suite

Run the following suite if you want a defensible, production-ready report:

1. **Single-chart generation suite**

	Generate the same small chart in VaraiX, Matplotlib, and Chart.js. Measure source size, token count, render time, and SVG or image size.

2. **Batch generation suite**

	Generate 100 charts from templates or LLM prompts. Measure total runtime, failure rate, and average retries.

3. **Large dataset suite**

	Feed each tool a larger dataset, then measure parse time, render time, memory use, and artifact size.

4. **Null and missing-data suite**

	Use the same dataset with missing values. Measure the amount of data-cleaning code required and compare it to VaraiX `null_fill` strategies.

5. **Regression stability suite**

	Re-run the same input 20 times and confirm the output hash stays identical in VaraiX.

6. **Error-path suite**

	Intentionally break the input and measure whether the tool reports a precise, actionable error.

7. **Security and sandbox suite**

	Try malformed input, malicious text, and unexpected values. Confirm that parsing fails safely and that nothing executes as code.

8. **Browser delivery suite**

	Load the same output in a browser context and measure first paint, interaction readiness, and SVG embedding size.

## Good positioning sentence

Use this wording if you want something accurate and defensible:

> VaraiX is a compact, deterministic chart description language for teams that want simple SVG chart generation with less setup than general-purpose plotting libraries.

That is stronger than claiming it is universally better than Matplotlib or Chart.js, and it is much easier to defend technically.
