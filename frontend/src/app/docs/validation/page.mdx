# Validation

This page documents what has been validated in the repository, how to reproduce the benchmark evidence, and why VaraiX is a stronger fit than a general-purpose Python or JavaScript charting stack for compact, deterministic SVG chart generation.

## Why VaraiX is better for this use case

VaraiX is better than Python Matplotlib or JavaScript Chart.js when the goal is not statistical analysis or highly interactive dashboards, but instead compact chart definitions that are easy to generate, diff, validate, and render deterministically.

That means it is a better fit when you care about:

- shorter source files that are easier to review
- lower token usage for LLM-generated charts
- deterministic SVG output
- simpler automation and CI validation
- less defensive code for null handling
- a smaller security surface because the input is parsed, not executed

## What has been validated

- The docs site builds successfully with the new comparison and validation pages.
- The benchmark harness runs against real `.vix` inputs and measures parse and render time.
- The results are saved in version control as a JSON snapshot for repeatability.
- The `Why Varaix` page stays focused on the language and positioning instead of benchmark data.

## Validation checklist

1. Build the frontend docs site.

2. Run the benchmark harness against the sample cases.

3. Save the JSON output from the benchmark run.

4. Compare the source size, token count, render time, and SVG size across cases.

5. Repeat the benchmark on a fresh machine or CI runner to verify stability.

## Benchmark command

Run this from the repository root:

```bash
cargo run --bin varaix-benchmark -- 10
```

The current measured output is stored in [benchmarks/results/latest.json](../../../../../../benchmarks/results/latest.json).

## Benchmark categories

These are the production-grade validation categories this repository should cover:

| Category | What it measures | Why it matters |
| --- | --- | --- |
| Source size and token count | How much source is needed to express the same chart | Shows compactness and LLM efficiency |
| Parse throughput | How fast a chart file is parsed | Matters for CI and batch generation |
| Render throughput | How fast SVG is produced | Core runtime cost |
| Cold start time | Time to first render in a fresh process | Important for CLI and browser startup |
| Warm run time | Repeated render latency after startup | Useful for bulk generation |
| Memory usage | Peak memory during parse and render | Matters for server and CI workloads |
| Output determinism | Whether repeated runs produce identical output | Critical for reproducible builds |
| Null handling behavior | How missing data is handled | Shows the value of `null_fill` |
| Error quality | Whether failures are clear and actionable | Helps debugging and automation |
| Security and sandbox behavior | How malformed or malicious input is handled | Reduces risk in shared systems |
| CI stability | Whether results are reproducible in automation | Prevents flaky benchmark claims |
